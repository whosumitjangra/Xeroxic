Abstract—Campus print facilities experience intense operational surges during assignment deadlines and examination cycles. Traditional in-person submission models—relying on physical queues, shared USB flash drives, or informal messaging channels—suffer from throughput bottlenecks, malware transmission risks, and opaque order tracking. This paper details Xeroxic, an end-to-end web platform engineered to modernize campus document intake, automated pricing, payment verification, and administrative queue management. To operate reliably within resource-bounded cloud environments, the system decouples control-plane operations from heavy document payloads: a Node.js serverless API validates file eligibility and grants scoped authorization, while raw document binaries stream directly between client browsers and Supabase object storage via time-limited pre-signed URLs. This direct-to-storage strategy circumvents the 4.5 MB request payload ceiling common to serverless runtimes. Security controls incorporate role-based authorization across student and administrative tiers, memory-hard scrypt credential hashing with synthetic dummy executions to eliminate user-enumeration side channels, tamper-evident HttpOnly session cookies, sliding-window rate limiting, and server-side HMAC-SHA256 verification of Razorpay payment callbacks. A comprehensive automated test suite consisting of 84 test cases verified functional state machines, perimeter defenses, and fallback routines. We analyze the architectural boundaries, evaluate the empirical test coverage, and outline operational requirements for campus-wide pilot deployment.

Index Terms—campus printing services, serverless computing, pre-signed upload URLs, role-based access control, cryptographic verification, web application security.

I. INTRODUCTION

Academic printing remains an indispensable everyday reality across collegiate institutions. Even in modern digitized universities, course coordinators, laboratory instructors, and administrative offices routinely mandate physical submissions for term papers, lab records, engineering drawings, and dissertations. Yet the physical counter experience has remained remarkably archaic. When hundreds of students converge upon a campus xerox center before morning submission deadlines, the counter becomes an overwhelming bottleneck. Document exchange typically takes place via unvetted USB flash drives plugged into shared counter terminals—a recognized vector for malware propagation—or through uncompressed chat messages where print attributes (color balance, paper weight, single versus double-sided orientation) are communicated verbally amidst chaotic counter noise. Pricing disputes, lost printouts, and uncertainty regarding queue positions are chronic daily friction points.

Designing a web-based management layer to streamline this intake encounters a fundamental cloud infrastructure bottleneck: serverless payload limits. Modern serverless platforms, including Vercel and AWS Lambda, deliver cost-effective automated elasticity well suited to intermittent campus demand, but impose rigid execution boundaries. Specifically, request body sizes are hard-capped between 4.5 MB and 6 MB. A typical academic submission—such as a 40-page scanned engineering report or an image-dense project portfolio—routinely spans 15 to 40 MB. Funneling raw file bytes through intermediate serverless function endpoints triggers severe memory pressure, prolonged connection timeouts, and HTTP 413 payload-size termination faults. Xeroxic resolves this structural limitation by strictly isolating application metadata from binary payloads: the API verifies identity and mints short-lived pre-signed storage tokens, allowing client browsers to upload document binaries directly into private object storage.

This work makes three primary contributions. First, it formalizes the campus counter workflow into an auditable five-stage state machine (REQUEST_RECEIVED -> ACCEPTED -> PRINTING -> READY -> COMPLETED) paired with memorable order identifiers to streamline physical pickups. Second, it implements an authorized direct-to-storage upload and metadata-confirmation protocol that completely eliminates binary proxying through serverless compute functions. Third, it evaluates the implementation across an 84-point automated test suite, systematically analyzing role boundaries, pricing integrity, payment signature verification, and scale limits, while defining a concrete governance framework for campus-wide adoption.


II. PROBLEM DEFINITION AND REQUIREMENTS

An effective campus printing portal must reconcile distinct operational expectations across student patrons and print center staff. Students require an intuitive mobile-friendly workflow: uploading eligible coursework files, configuring print parameters (color vs. grayscale, single-sided vs. double-sided, binding options, copy counts), previewing server-verified price quotes, and tracking order readiness in real time. Shop technicians, conversely, need an auditable, prioritized queue where incoming paid jobs can be inspected and transitioned through standard production milestones without accidental cross-user document leakage. Crucially, pricing logic must reside entirely on the server; client-submitted totals are treated strictly as untrusted requests and recalculated against authoritative rate records.

Tenant isolation and data protection are fundamental constraints. Academic submissions contain sensitive intellectual property, graded assessments, and personal student information. File metadata records explicitly link each document to an authenticated owner identifier and a scoped object path. System routes enforce strict role separation among students, shop administrators, and super-administrators, rejecting unauthorized role escalation. To reduce the file-intake attack surface, the upload validation pipeline accepts only standardized academic file formats (PDF, DOCX, PPTX, TXT, and common raster imagery), actively rejecting executable binaries, scripts, and active web formats.

III. RELATED WORK AND DESIGN RATIONALE

Function-as-a-Service (FaaS) environments offer compelling economic advantages for campus services because execution resources automatically scale to absorb peak traffic during midterms and finals while scaling to zero cost during academic breaks [1], [2]. However, handling high-volume binary data within containerless runtimes has long been recognized as an architectural anti-pattern. Streaming heavy multipart payloads through short-lived function runtimes exhausts ephemeral container memory and triggers gateway timeouts [3]. Modern object storage services, including Supabase Storage and Amazon S3, resolve this tension by providing pre-signed URL primitives [4]. By generating time-delimited, cryptographically signed upload and retrieval URLs on the server, applications delegate high-bandwidth data transfers directly to high-throughput cloud storage engines.

Traditional campus print management platforms (such as CUPS and PaperCut) operate primarily as network printer spoolers requiring dedicated local servers, domain authentication, and vendor-specific print drivers. In typical college copy shops, however, multi-function copiers are directly connected to local operator PCs rather than enterprise networks. Xeroxic deliberately targets the application-layer workflow—file ingestion, price calculation, digital payment, and queue tracking—leaving the final physical print command to counter operators. This lightweight approach avoids complex driver integration while delivering comprehensive end-to-end order accountability.

Security mechanisms throughout the platform follow defense-in-depth principles rather than superficial interface validation [5]. Student credentials are protected via the scrypt key derivation function, whose memory-hard architecture offers robust resistance against specialized ASIC and GPU brute-force attacks [7]. User sessions utilize signed, HttpOnly cookies with SameSite=Lax flags, preventing script-based token extraction and reducing cross-site request forgery risks. For financial transactions, Razorpay's server-verification model was implemented: checkout signatures are validated via HMAC-SHA256 digests over concatenated gateway identifiers [8], [10], evaluated with timing-safe comparison primitives [9] to neutralize timing side-channel attacks.

Alternative architectures were evaluated during system design. A traditional monolithic backend buffering multipart file uploads in server RAM was rejected due to vertical scaling costs and provider timeout thresholds. Storing document content directly as binary fields within database records was dismissed due to storage bloat and slow query performance. A fully public storage bucket was considered unacceptable because academic documents must remain strictly confidential. Xeroxic adopts an optimal hybrid paradigm: the Node.js serverless API retains exclusive ownership over authorization, pricing, and metadata indexing, while the underlying object store manages secure, isolated binary storage.

IV. SYSTEM ARCHITECTURE


Fig. 1. Xeroxic separates authorization and metadata processing from the intended direct object-store transfer.

A. Application tiers

The presentation tier is implemented with standard semantic HTML5, responsive CSS3, and modular vanilla JavaScript. It delivers distinct, role-tailored interfaces for students, shop administrators, and super-administrators without heavy client-side framework overhead. The control tier is a single Node.js request router that can run behind Vercel routing or through a local HTTP server. It parses requests, verifies session tokens, enforces route roles, calculates order totals, and calls persistence and storage adapters. The persistence adapter supports JSON-backed local storage for development and MongoDB Atlas when configured. Document content is intentionally represented as an object path and metadata record rather than as a database binary field.

B. Direct upload and retrieval

For a direct upload, the browser first calls /api/files/prepare-upload with filename, byte size, and MIME type. The server normalizes the filename, enforces an extension allowlist, rejects declared sizes exceeding 50 MB, and constructs a tenant-scoped path under students/{userId}/. It then requests a signed upload URL from Supabase Storage. Following the browser's direct transfer, /api/files/confirm-upload verifies that the reported path begins with the authenticated student's prefix and persists only the metadata. The intended effect is to keep document bytes entirely out of the serverless function, bypassing the execution payload ceiling noted in [3].

For retrieval, a file record is located by identifier and access is allowed only to its owner or a recognized staff role. If the record holds an object-store path, the service generates a temporary signed download URL with a one-hour expiry window; otherwise, the local-file route serves the stored fallback. Signed URLs serve as a delivery mechanism rather than a substitute for authorization: access validation strictly precedes URL issuance [4].

C. Order and assignment workflow

An order encapsulates user identity, item specifications, pricing attributes, total amount, payment status, and fulfillment state. The backend derives line amounts as rate x pages x copies and sums submitted items against authoritative pricing schedules. A paid request becomes visible to counter staff, who advance the workflow across REQUEST_RECEIVED, ACCEPTED, PRINTING, READY, and COMPLETED. To assist campus communication, an assignment hub allows staff to publish syllabus sheets and lab manuals for student viewing and printing.

D. Trust boundaries and failure behavior

Figure 1 highlights the critical operational trust boundaries. The student browser is treated as an untrusted client: requested page counts, filenames, payment states, and URL parameters are all subject to server-side validation. The API manages server secrets and enforces business logic. Object storage hosts binary payloads under strict bucket policies to prevent cross-tenant enumeration. Razorpay provides independent financial settlement, while the internal database tracks workflow progression. This separation makes failure modes predictable: a storage interruption cannot create a ghost file record, and an unverified payment cannot dispatch a print request.

The codebase includes development fallbacks to support offline local testing. While beneficial during rapid prototyping, these fallbacks alter assurance levels. For example, a simulated order identifier demonstrates that the HMAC verification route handles expected string shapes, but cannot prove bank settlement. A production deployment must disable local simulation paths and fail closed whenever external verification services are unavailable.

V. IMPLEMENTATION DETAILS

A. Authentication and session handling

User credentials are salted with 16 cryptographically random bytes and hashed using Node's synchronous scrypt interface (N = 16384, r = 8, p = 1, 64-byte key). A synthetic dummy scrypt calculation executes whenever an unregistered email is queried, equalizing response times to prevent account-enumeration timing leaks. Sessions utilize base64url payloads signed with HMAC-SHA256, encapsulating user identifier, name, email, role, and a seven-day expiration. Tokens are transmitted within HttpOnly, SameSite=Lax cookies, with the Secure flag enforced in production environments. Authentication endpoints are guarded by an in-memory sliding-window IP rate limiter to mitigate automated brute-force attacks.

API responses apply no-store cache directives and defense-in-depth security headers, including X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN, Referrer-Policy, and HSTS. These controls follow established web security practices [5] to protect students against common browser-level attack vectors.

B. Payment verification

The payment module provides both a local testing route and a live Razorpay integration. In the Razorpay route, /api/create-order generates a gateway order from a server-verified total. Upon completion, /api/payments/verify reconstructs HMAC-SHA256(order_id || "|" || payment_id, key_secret) and evaluates it against the received signature using crypto.timingSafeEqual. Only a cryptographically verified signature transitions an order to PAID, and the internal order must strictly match the active student session.

C. Deployment configuration

The persistence layer implements a flexible repository pattern, supporting atomic JSON files for local development and MongoDB Atlas when MONGODB_URI is supplied. When deployed to Vercel, the local adapter seeds temporary data into /tmp, functioning as an ephemeral demonstration environment. Production deployment requires durable database storage, an immutable SESSION_SECRET, private bucket policies, and active webhook monitoring. Storage adapters include fallback mechanisms for development, but production instances should fail closed on storage errors.

D. Data model and consistency

The data model is lightweight and document-centric. User records maintain identity, role, salt, and password hash. File records track file identifiers, owner IDs, original names, storage keys, bucket names, sizes, and MIME types. Order records bind user identity, item attributes, computed totals, payment methods, and status timestamps. Print-request records emerge upon successful payment, serving as actionable queue items. Notifications reference order identifiers to keep pending and paid status displays synchronized.

E. Operational sequence

A standard print request follows a predictable sequence. The student signs in, selects a valid file, and receives upload authorization. The browser transfers the file directly to object storage and confirms metadata. The student specifies print attributes, prompting the server to calculate the authoritative total and initiate a payment order. Following payment, the server validates the signature, marks the order PAID, and queues the job. Staff inspect the file via authorized download links and advance the order state. The student observes live status updates without ever gaining direct access to underlying storage buckets or peer records.

VI. SECURITY ANALYSIS

The primary authorization concern in multi-tenant portals is Insecure Direct Object References (IDOR), where an adversary modifies an order or file identifier to inspect another student's document. Xeroxic mitigates IDOR by validating owner identifiers against the authenticated session across all download, order retrieval, and payment endpoints. Administrative access requires explicit role validation. Automated test cases verify cross-student isolation and student-to-administrator access rejection.

File-upload threats include malicious executable execution, path traversal, oversized payloads, and persistent storage pollution. Xeroxic normalizes submitted filenames, enforces a strict file-extension allowlist, generates object keys server-side, and rejects confirmation paths that deviate from the user's assigned prefix. Institutional deployments should further augment this perimeter with MIME validation, antivirus scanning, and least-privilege storage bucket policies as recommended by OWASP [6].

A. Authentication attack surface

Password hashing, generic error messaging, and IP rate limiting provide layered defense against credential attacks. scrypt increases the computational complexity of offline dictionary attacks [7]. Dummy hashing neutralizes timing differences between valid and invalid usernames. Rate limiting restrains rapid automated login attempts. HttpOnly cookies prevent client-side script token theft, while SameSite=Lax mitigates basic cross-site request forgery. Administrative portals should further enforce multi-factor authentication (MFA) in production.

B. Authorization and storage attack surface

Resource identifiers serve strictly as references, never as authorizations. Signed-URL routes verify record ownership and staff permissions before requesting storage tokens. Upload confirmations verify path prefixes before persisting metadata. Similarly, order verification requires an exact match between the session identity and the order's owner identifier. Enforcing these checks at the API layer ensures access control remains intact regardless of external storage permissions.

C. Payment attack surface

Payment verification resists client-side tampering by computing signatures with a server-held secret. The system rejects incomplete payloads, mismatched signatures, and attempts to verify an order belonging to another student. Production deployments should further incorporate webhook replay prevention, unique transaction tracking, settlement reconciliation, and alert mechanisms for indeterminate payment states.

D. Privacy and availability

Academic files frequently contain intellectual property, graded assessments, or sensitive personal data. Role-based access, temporary download links, and private storage reduce unauthorized exposure. File auto-purge routines delete completed document binaries from storage, conserving quota and protecting student privacy. System availability is maintained through clear error propagation, preventing network or service hiccups from creating orphaned print jobs.

VII. EVALUATION

The platform was evaluated through an automated test suite (npm test) executed within the local project environment. The test harness completed 84 named checks across six functional domains with a 100% pass rate. Test categories included session management, static asset delivery, file operations, order tracking, role boundaries, assignment distribution, notification feeds, rate limiting, Razorpay signature validation, direct-upload handshakes, scale limits, and latency targets. The test execution confirms control-flow correctness, route authorization integrity, and graceful fallback handling under the tested environment.

A. Test methodology

The test suite invokes the primary serverless request handler and evaluates HTTP response codes, headers, cookie values, and database records. The testing workflow begins by confirming authentication and static routing, creating a student profile, executing fallback file uploads, and validating download permissions. It then logs into seeded administrator and super-administrator accounts to evaluate role boundaries, dynamic pricing updates, assignment publication, and notification dispatching. Adversarial tests verify HTTP 403 responses on unauthorized administrative access and HTTP 429 responses under excessive login traffic.

It confirms that route handlers, role middleware, and cryptographic routines behave as intended. However, integration tests using localized fallbacks cannot independently establish cloud storage availability or bank transaction settlements. Transparent reporting of fallback conditions ensures clear differentiation between verified code logic and live field operations.

VIII. LIMITATIONS AND FUTURE WORK

Xeroxic currently functions as an application-level print request manager; counter staff manually initiate physical printing after reviewing submitted documents. It does not yet include automated spooler dispatchers to physical printers via IPP or CUPS network daemons. Development fallbacks must be strictly disabled prior to production deployment. Future development will focus on automated ClamAV antivirus scanning prior to staff retrieval, automated duplex page-count analysis via PDF binary parsing engines, and real-time push notifications over WebSockets.

A phased deployment roadmap is envisioned: Phase 1 conducts production configuration audits (rotating development secrets, deploying managed MongoDB clusters, and enforcing strict Supabase RLS policies). Phase 2 introduces institutional Single Sign-On (SSO) integration via Google Workspace / SAML and automated webhook reconciliation for financial audits. Phase 3 pilots direct IPP spooler bridges within high-volume departmental print labs.

IX. DEPLOYMENT READINESS AND PILOT PROTOCOL

Institutional deployment demands disciplined configuration governance. All runtime secrets (SESSION_SECRET, storage service keys, and payment credentials) must be managed through secure platform key stores rather than local configuration files. Object storage buckets must enforce private access control with zero public read permissions, allowing object retrieval solely through time-limited signed URLs. Dependency trees should be locked and monitored for known vulnerabilities.

A structured campus pilot protocol should initially operate alongside existing counter workflows. Key performance indicators to monitor include queue turnaround times, payment reconciliation accuracy, file intake error rates, and counter operator throughput. Clear incident response procedures must be established for payment discrepancies, file formatting discrepancies, and hardware jams, ensuring that technical dependency faults never disrupt student assignment submissions.

Finally, governance policies should treat submitted documents as institutional records. Campus policies must define retention windows for completed orders, authorized staff access roles, and formal deletion schedules. After the pilot demonstrates operational stability, printer spooler integrations can be safely introduced within isolated network zones.

X. CONCLUSION

This paper presented Xeroxic, a lightweight, serverless print request management system designed to eliminate congestion and operational friction at campus print facilities. By decoupling control-plane authorization from data-plane binary transfers, the architecture enables high-capacity document uploads without exceeding serverless memory and payload limits. Security-first engineering—featuring scrypt password derivation, tamper-proof session tokens, role-based boundary enforcement, and server-side HMAC payment verification—safeguards student data and financial transactions. Validated across an 84-point automated test suite, Xeroxic demonstrates how lightweight serverless architectures can effectively modernize academic print services, establishing a dependable foundation for institutional deployment.
